## 【背景与需求】
- 背景/现状：仓库同时存在旧版静态 WebUI（根目录 `index.html` + `app.js` + `src/`）与 Next.js 重写版（`next-app/`）；Next 版已覆盖 Usage/Logs/Pipeline/Pricing 等部分能力，但旧版仍承载“基础设置 / API 密钥 / Providers / Auth Files / Config / System / OAuth / 连接配置”等核心功能。
- 痛点：
  - 双入口/双实现：用户与维护者都不确定应以哪个入口为准，功能割裂、维护成本高。
  - 旧版 DOM/原生 JS 模块形态扩展困难：状态分散、页面组织以 hash+section 为主，不利于做更复杂的交互与演进。
  - Next 版侧边栏已有链接但缺少对应页面（例如 `/login`、`/settings`、`/auth-files`、`/config`、`/system`），存在断链风险。
  - 数据与安全边界不统一：usage 已引入 DB 与聚合，而 settings/config 等仍在旧版直连 management API，需要统一“路由层/页面层/数据访问层”边界。
  - i18n 两套并存：旧版 `i18n.js` 与 Next 版 `components/i18n-context.tsx`，迁移期容易新增硬编码导致维护成本上升。
- 需求/用户价值：
  - 统一入口：以 `next-app/` 为唯一入口，减少双入口维护成本与用户困惑。
  - 提升体验：界面更美观、交互更完整（状态覆盖、危险操作确认、可恢复的错误提示）。
  - 可扩展：后续新增模块沿用统一的页面骨架与数据访问边界。
- 范围（做什么）：
  - 补齐路由：`/login`、`/settings`、`/settings/providers`、`/auth-files`、`/config`、`/system`，并确保侧边栏无断链。
  - 迁移模块：Settings、API Keys、AI Providers、Auth Files、Config Editor、System Info、OAuth/连接配置、主题/语言入口一致化。
  - 数据策略：允许 Next 增加 API route 与 DB（主人选择 B）；敏感密钥默认只存在服务端 env，不落库、不暴露到客户端。

## 【目标】
- 在 `next-app/` 内实现旧版 `src/` 下“剩余全部功能”的等价能力（按旧侧边栏颗粒度：基础设置、API Keys、AI Providers、Auth Files、Config、System、OAuth/连接配置等），并保证已迁移模块（Usage/Logs/Pipeline/Pricing）不回归。
- `src/` 保留但不再作为入口；默认入口切到 `next-app/`（旧入口仅用于对照/回滚）。
- UI 与交互达到统一且现代：一致的布局/信息层级/组件规范，完善的状态（loading/empty/error/disabled/confirm），并遵循 i18n（中英双语）。
- 架构清晰可扩展：页面/组件/数据访问（management API + DB）职责边界明确；复杂逻辑沉到 `lib/`，避免“页面文件无限膨胀”（单文件>600 行必须拆分）。

## 【非目标】
- 不删除/重写旧版 `src/` 静态 WebUI（按主人要求“保留，但不作为入口”）。
- 不引入真正的用户体系/角色权限（仓库当前无权限系统；迁移后保持旧版功能颗粒度即可）。
- 不改变 CLIProxy 后端管理 API 的语义与权限校验逻辑（只做前端迁移与体验提升）。
- 不新增 CI/CD 自动化（构建/测试由主人手动执行）。

  - Next 现有模块（Usage/Logs/Pipeline/Pricing）不回归。
