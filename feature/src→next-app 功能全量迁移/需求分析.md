# src→next-app 功能全量迁移 - 需求分析（生成时间：2025-12-26 14:40）

## 背景与现状
- 背景：CLIProxy Management Center 当前存在两套 UI：旧版静态 WebUI（根目录 `index.html` + `app.js` + `src/`）与 Next.js 重写版（`next-app/`）。主人要求把旧版 `src/` 下剩余功能全部迁移到 `next-app/`，并提升 UI 美观度与交互质量。
- 现状/痛点（带证据锚点）：
  - 旧版以 hash/section 组织页面，模块颗粒度清晰但扩展成本高：
    - 证据：`index.html` 的 `<nav class=\"sidebar\">` 与 `<section id=\"...\">`（如 `#basic-settings`、`#api-keys`、`#ai-providers`、`#auth-files`、`#usage-stats`、`#config-management`、`#logs`、`#system-info`）。
  - Next 版已有侧边栏导航，但缺少若干关键路由目录，存在断链风险：
    - 证据：`next-app/components/layout/sidebar.tsx` 已包含 `/login`、`/settings`、`/auth-files`、`/config`、`/system` 等链接，但 `next-app/app/` 下暂无对应目录。
  - 数据边界不统一：Next 版已引入 Prisma/DB 用于 usage/pipeline/pricing，而旧版 settings/config 等直连 management API；迁移需要统一“server-only 代理访问管理 API”的策略，避免密钥暴露到客户端：
    - 证据：`next-app/lib/cliproxy-client.ts` 使用服务端 env 调用管理 API；`next-app/app/api/logs/route.ts` 等 route handler 已存在。

## 用户/角色
- 单一操作者（运维/开发者/管理员）。本任务不引入账号/角色权限系统；迁移后保持旧版功能颗粒度与可访问性即可。

## 目标与范围
- 目标（可验证）：
  - G1：`next-app/` 覆盖旧版 `src/` 下剩余模块的等价能力（按旧侧边栏颗粒度：基础设置、API Keys、AI Providers、Auth Files、Config、System、OAuth/连接配置）。
  - G2：默认入口切换到 `next-app/`；旧版 `src/` 保留但不作为入口（用于对照/回滚）。
  - G3：UI/交互统一提升：一致的布局/信息层级/组件风格，完善状态（loading/empty/error/confirm/disabled），并严格 i18n（en/zh）。
  - G4：可扩展架构：页面/组件/数据访问（management API + DB）职责边界清晰；单文件>600 行必须拆分。
- 范围（做）：
  - 路由补齐：`/login`、`/settings`、`/settings/providers`、`/auth-files`、`/config`、`/system`（与 next-app 侧边栏一致）。
  - 旧模块迁移：Settings、API Keys、AI Providers、Auth Files、Config Editor、System Info、OAuth、主题/语言入口一致化。
  - 数据策略：允许 Next 增加 API route 与 DB（主人已选择 B）；敏感密钥默认不落库，优先使用服务端 env。
- 非范围（不做）：
  - 不删除旧版 `src/`；不做全仓无关重排/格式化。
  - 不引入真正的用户登录/权限体系（无 RBAC/无鉴权）。
  - 不改变后端管理 API 的语义与权限规则；只做前端迁移与体验提升。
  - 不新增 CI/CD 自动化。

## 路由与模块映射（旧 → 新）
- 旧 `#basic-settings` + `#system-info`（混合基础设置与系统信息）→ 新 `/settings` + `/system`
- 旧 `#api-keys` → 新 `/settings/api-keys`（建议）或 `/settings` 内 Tab（以 UI 设计稿为准）
- 旧 `#ai-providers` + `#oauth`（页面内卡片）→ 新 `/settings/providers`
- 旧 `#auth-files` → 新 `/auth-files`
- 旧 `#config-management`（Config Editor）→ 新 `/config`
- 旧 `#logs` → 新 `/logs`（next-app 已存在；补齐与旧版等价能力与体验差异）
- 旧 `#usage-stats` → 新 `/usage`（next-app 已存在；补齐/对齐旧版“API 详细统计”等能力）
- 说明：
  - 旧入口（静态 UI）按主人要求保留，但不作为默认入口。
  - 迁移后 Next 侧边栏不得出现断链（有导航项就必须有路由页面）。

## 核心场景（3-6条）
- 场景1：连接/健康检查（`/login`）
  - 用户打开管理台后，能看到连接目标、连接状态、服务端版本等信息；当 env 缺失/连接失败时给出可操作的修复指引。
- 场景2：基础设置（`/settings`）
  - 读取并更新 Debug、Proxy URL、Request retry、Usage 统计开关、Request log、WS Auth、Logging-to-file、Quota exceeded 策略等；失败时 UI 回滚并提示原因。
- 场景3：API Keys 管理（`/settings/api-keys` 或 `/settings` Tab）
  - 查看/新增/编辑/删除 key；支持复制与遮罩显示；保持旧版自定义 header 编辑能力（如仍适用）。
- 场景4：Providers & OAuth（`/settings/providers`）
  - 管理 Gemini/Codex/Claude 等 provider key；获取 OAuth URL 并进行跳转/回填；状态清晰可追踪。
- 场景5：Auth Files（`/auth-files`）
  - 查看/筛选/搜索/分页；展示类型/更新时间/大小/成功失败统计；下载/删除（危险操作二次确认）。
- 场景6：Config & System（`/config`、`/system`）
  - Config Editor：读取/编辑/保存配置（YAML/文本），提供脏态提示、冲突处理、快捷操作。
  - System：查看 UI 版本/服务端版本/构建时间/连接信息，作为排障入口。

## 数据对象与字段（关键即可）
- Connection（连接信息）
  - apiBase、managementKey（默认服务端 env 管理）、isConnected、serverVersion/serverBuildDate、uiVersion。
- Settings（配置与开关，旧版已覆盖）
  - debug: boolean
  - proxy-url: string
  - request-retry: number
  - usage-statistics-enabled: boolean
  - request-log: boolean
  - ws-auth: boolean
  - logging-to-file: boolean
  - quota-exceeded: { switch-project: boolean; switch-preview-model: boolean; ... }
- API Keys
  - apiKeys: string[]
  - customHeaders?: Record<string, string>
- Provider Keys / Provider Config
  - gemini-api-key / codex-api-key / claude-api-key
  - openai-compatibility: { ... }
  - oauthUrl: string（按 provider endpoint 获取）
- Auth Files
  - AuthFile: { name: string; type: string; modtime: number; size: number; authIndex?: string; runtimeOnly?: boolean; ... }
  - AuthFileStats: { success: number; failure: number; ... }
- Logs
  - lines: string[]；latestTimestamp；lineCount；支持 after/limit 增量。

## 接口/数据来源
- 管理 API（CLIProxy Management API）：用于 settings、keys、auth-files、logs、usage 等实时数据与配置写入。
- DB（Prisma/Postgres）：用于 usage/pipeline/pricing 的聚合、会话等分析数据（next-app 现状已使用）。
- 旧版已使用的 management endpoints（迁移期必须覆盖，按“等价能力”验收）：
  - Settings：`/debug`、`/proxy-url`、`/request-retry`、`/usage-statistics-enabled`、`/request-log`、`/ws-auth`、`/logging-to-file`、`/quota-exceeded/*`
  - Keys/Auth/Usage/Logs：`/api-keys`、`/auth-files`、`/usage`、`/logs`
  - OAuth/Providers：`/codex-auth-url`、`/anthropic-auth-url`、`/gemini-cli-auth-url`、`/qwen-auth-url`、`/iflow-auth-url`…；`/gemini-api-key`、`/codex-api-key`、`/claude-api-key`、`/openai-compatibility`
- 缓存/轮询建议（由实现方案细化）：
  - Logs：增量拉取（after）+ 上限（limit）+ 自动刷新可开关。
  - Settings：页面加载读取；更新后局部刷新并回滚失败状态。
  - Auth Files：列表读取后本地分页/筛选，必要时提供手动刷新入口。

## 文案与 i18n（强制）
> 主人已确认：本次会新增/修改用户可见文案，必须走 i18n。

- 现状：Next 版使用 `next-app/components/i18n-context.tsx`（`en/zh` 字典 + `useI18n().t(key)`），侧边栏已使用 `nav.*` key。
- 约束：新增页面/组件所有文案必须使用 `t(key)`，禁止硬编码中文/英文。
- key 命名策略（建议）：
  - 导航：`nav.*`（沿用现状）
  - 页面：`<route>.title` / `<route>.subtitle`（如 `settings.title`）
  - 表单：`<route>.form.<field>.*`（label/placeholder/help）
  - 动作：`actions.<verb>` 或 `<route>.actions.<verb>`
  - 通知/错误：`toast.*` / `<route>.error.*`
- 文案清单（按页面，初稿；UI 设计阶段补齐）：
  - `/login`：连接状态、缺失 env 提示、重试、配置指引
  - `/settings`：各项开关/输入项 label、保存/重置、成功/失败提示
  - `/settings/providers`：provider key 管理、连通性提示、OAuth 跳转/回填提示
  - `/auth-files`：筛选/搜索/分页、下载/删除确认、空态/错误态
  - `/config`：脏态、保存/重载/下载、语法错误提示
  - `/system`：版本/连接信息、复制、诊断提示

## 约束与假设
- 技术栈约束：Next.js App Router、React 19、TypeScript、Tailwind CSS 4、shadcn/ui、Prisma（Postgres）。
- 依赖与安全：
  - 允许新增 Next API route 与 DB 表/字段（主人选择 B）。
  - 管理密钥默认只存在于服务端环境变量（`CLIPROXY_MANAGEMENT_KEY`），页面只调用 Next 的 `/api/*`。
  - 未获得《实现方案.md》“主人确认”前，不进行业务实现代码改动（仅产出文档/方案）。
- 性能/体验：
  - 列表/日志类页面避免一次性渲染过多 DOM；提供分页/增量/节流策略（以实现方案为准）。
  - Loading/Empty/Error 必须可见且可恢复；危险操作必须 confirm。

## 边界条件
- 状态覆盖：
  - loading / empty / error / disabled / confirm（本任务不做权限不足态，但要保留扩展位）。
- 极端与异常：
  - 数据量大（日志行很多、auth files 很多）时保持可用（限制 + 分页/虚拟列表）。
  - management API 不可达、返回非 2xx、返回结构缺失字段（前端容错与提示）。
  - 配置编辑包含超长文本/非法 YAML（需要错误提示与不丢内容的回滚策略）。

## 验收标准（可验证）
- 视觉/交互：
  - 与现有 next-app 视觉统一（主题、间距、卡片/表单、图标风格一致），交互反馈完整（hover/focus/disabled/confirm/toast）。
  - 支持中英切换（i18n 字典完整，新增页面无硬编码）。
- 功能：
  - 旧版 `src` 下剩余模块均可在 `next-app` 中访问并完成主流程操作（按“路由映射表 + 功能清单”验收）。
  - Next 现有模块（Usage/Logs/Pipeline/Pricing）不回归，侧边栏无断链。
- 性能：
  - 日志拉取有上限（limit）且支持增量（after）；默认数据量下交互流畅。
- 可维护性：
  - 单文件>600 行必须拆分；数据访问逻辑集中在 `lib/` 或 `app/api/*`；类型定义集中且可复用。

## 风险与回滚
- 风险：
  - management API 字段/行为与旧版假设不一致，迁移细节容易偏差。
  - 若把管理密钥暴露到客户端会增加泄漏风险；必须优先采用 server-only 代理策略。
  - 页面多、交互多，容易出现 UI 风格碎片化，需要 UI 设计阶段统一规范。
- 回滚：
  - 入口回滚：把默认入口切回旧静态 UI（旧版按主人要求保留）。
  - 分批落地：按模块分批实现，单模块可独立回退，降低一次性大改风险。
