# 实现方案（生成时间：2025-12-19 13:47）

## 最终数据结构（TypeScript / Prisma）
### Prisma（数据库）
- 目标：允许“同一天 + 不同筛选条件”的任务共存，并落库筛选条件。
- 改动建议（最小可上线）：
  - `UsageAggregateJob` 增加：
    - `filters Json? @db.JsonB`（存 { models?: string[]; channels?: ("cliproxy"|"codex")[] }）
    - `filtersHash String @default("all")`（筛选条件指纹，用于唯一性）
  - 将唯一索引从 `@@unique([kind, rangeFrom])` 调整为 `@@unique([kind, rangeFrom, filtersHash])`。
- 不修改 `UsageDaily` 结构：渠道口径沿用现有“由 apiPath 归类 codex/cliproxy”的事实标准（详见“聚合逻辑与渠道口径”）。

### TypeScript（接口/状态模型）
```ts
export type UsageChannel = "cliproxy" | "codex";

export type UsageAggregateJobFilters = {
  models?: string[];   // undefined 表示全量
  channels?: UsageChannel[]; // undefined 表示全量
};

export type UsageAggregateJobCreateRequest = {
  kind?: "daily";
  from: string; // ISO (UTC)
  to: string;   // ISO (UTC)
  force?: boolean;
  filters?: UsageAggregateJobFilters;
};

export type UsageAggregateMetaResponse = {
  channels: UsageChannel[];
  models: string[];
  earliestEventTime: string | null; // ISO UTC
  earliestUtcDate: string | null;   // YYYY-MM-DD
  yesterdayUtcDate: string;         // YYYY-MM-DD
};
```

## 关键实现策略与口径统一
### 渠道口径统一（重要）
- 渠道定义必须沿用现有 Usage API 的口径：`apiPath ∈ codexApiPaths => codex`，否则 cliproxy。
- 原因：`app/api/usage/route.ts` 中 channel 维度已按 apiPath 归类，避免“同数据两套口径”错账。
- 结论：聚合时的 channels 过滤应基于 apiPath 条件，而不是 `UsageEvent.sourceType`。

### 时区处理
- 后端聚合仍按 UTC 日界限（与现有逻辑一致）。
- 前端显示为本地时区格式化，但提交时统一转换为 UTC 日起止。
- 预览区须提示“UTC 聚合，本地展示”的说明。

## 接口设计
### 1) 新增元数据接口（用于模型列表与最早时间）
新增文件：`app/api/usage/aggregate/meta/route.ts`
- 请求：`GET /api/usage/aggregate/meta`
- 响应：`UsageAggregateMetaResponse`
- 逻辑：
  - `models`: UsageEvent 去重 model（按字母排序）
  - `earliestEventTime`: UsageEvent 最早 eventTime
  - `earliestUtcDate`: earliestEventTime trunc 到 UTC day
  - `yesterdayUtcDate`: UTC 昨天日期
  - `channels`: 固定 `[cliproxy, codex]`

### 2) 可选：筛选条件变化时的最早时间
新增文件：`app/api/usage/aggregate/earliest/route.ts`
- 请求：`POST` body `{ filters?: { models?: string[]; channels?: UsageChannel[] } }`
- 响应：`{ earliestEventTime: string | null; earliestUtcDate: string | null }`
- 逻辑：在 UsageEvent 上加 filters 条件查询 MIN(eventTime)。

### 3) 扩展创建任务 API
更新文件：`app/api/usage/aggregate/jobs/route.ts`
- `usageJobCreateSchema` 增加 `filters`。
- 生成 `filtersHash`（排序去重后的稳定字符串 + hash）。
- `createPayload` 写入 `filters` 与 `filtersHash`。
- `force` 仅更新相同 `filtersHash` 的任务记录，避免误覆盖。

## 聚合逻辑改造
更新文件：`lib/usage-aggregate.ts`
- `backfillUsageEventCost` 与 `runUsageDailyAggregation` 增加 `filters` 参数。
- 通过 Prisma.sql 动态 WHERE 构造：
  - models: `AND "model" = ANY($models)`
  - channels:
    - 仅 codex：`AND "apiPath" = ANY($codexApiPaths)`
    - 仅 cliproxy：`AND NOT ("apiPath" = ANY($codexApiPaths))`
    - 两者都选/未传：不加条件
- 避免 SQL 注入：使用 `Prisma.join` / 绑定参数。

## 风险与回滚
### 主要风险
- 口径漂移风险：channels 过滤若与 Usage API 的 apiPath 口径不一致会错账  
  - 规避：统一使用 codexApiPaths 口径；建议抽离为服务端共享 helper。
- 唯一索引调整风险：变更 unique 可能影响旧代码  
  - 规避：filtersHash 默认 "all"；旧请求不带 filters 时兼容。
- 最早时间点查询性能：UsageEvent 量大时 MIN 查询可能慢  
  - 规避：可加索引 `@@index([eventTime])` 或加缓存。
- UsageDaily 新增唯一索引风险：历史重复数据会导致迁移失败  
  - 规避：上线前先用 SQL 检查重复组合并清理（或先手动确认无重复再执行迁移）。

### 回滚策略（🧯）
- 代码回滚：保留 DB 新增字段不影响旧逻辑（filters 可空）。
- 若 earliest 接口异常：前端降级为手动选择日期（显示告警，不阻断创建）。
