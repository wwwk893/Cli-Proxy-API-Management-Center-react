# 控制台概览页统计看板 - 需求分析

- 时间戳：2026-01-04

## 背景与现状
当前“控制台（/）”页面几乎为空，只能作为导航入口；而实际需要关注的信息分散在多个 Tab（用量统计、日志、数据管线、系统、设置、计费与价格、模型提供商等）。

用户在日常使用中最常见的问题是：
- 过去 24h 花了多少钱？用量是否异常？哪些模型/渠道贡献最大？
- 系统是否连接正常？数据管线是否堆积/失败？是否需要我立刻处理？
- 配置是否齐全（API Keys/Providers/价格表/关键开关），是否存在“隐性风险”导致后续故障？

## 用户/角色
- 管理员/运维：关注稳定性、管线健康、可操作的待处理事项。
- 运营/成本负责人：关注成本与用量态势、Top 模型贡献、异常增长。

## 目标与范围
### 目标（优先级：A → B → C）
- A 成本/用量态势（默认过去 24h）：在 10 秒内看清成本、tokens、请求量/事件量、Top 模型贡献与趋势。
- B 稳定性/告警摘要：系统连接状态、管线 pending/failed、（可选）日志错误概览，并提供跳转与行动入口。
- C 配置健康度：以“覆盖度/缺失提示”方式呈现 Providers/API Keys/价格表/关键开关状态。

### 范围（做）
- 新增一个“统计概览驾驶舱”页面：复用 `/` 路由替换占位内容。
- 顶部全局过滤：时间窗（今日UTC/过去24h/过去7天/过去30天）+ 渠道（全部/cliproxy/codex）。
- KPI 卡片（<=6）：成本、总 tokens、请求量/事件量、cached 占比、活跃会话（可选）、系统连接/版本。
- 图表区：一张主趋势（Cost 默认）+ Top Models 列表（按 Cost 默认）。
- 摘要区：稳定性卡（管线/日志/系统）+ 配置健康卡（providers/api keys/pricing/settings）。
- Action Center：最多 3–5 条待处理事项，必须可点击并指向下一步动作。

### 非范围（不做）
- 不重做“用量统计/日志”页的深度分析功能（概览只做摘要与跳转）。
- 不引入可配置告警规则系统（阈值编辑/通知/订阅）。
- 不做同比/环比/预算预测等二期能力。

## 核心场景（3-6条）
1) 管理员打开控制台：先看系统连接与管线健康；如失败/堆积，直接跳转到数据管线处理。
2) 成本负责人打开控制台：先看过去 24h 成本与 Top 模型贡献；点击进入用量统计深挖。
3) 新部署/新环境：通过配置健康度快速发现缺少 provider keys / 缺少价格表配置 / 关键开关关闭。
4) 异常排查：看到错误升高或管线失败→跳转日志/系统诊断。

## 数据对象与字段（关键即可）
- Usage 概览指标：`costUsd`、`totalTokens`、`cachedTokens`、`requestCount`、`latestEventTime`、按 `model` 的 top 列表、按时间桶的 trend。
- 管线健康：聚合任务状态计数（pending/running/failed/completed）、最近失败任务列表（id/range/lastError/updatedAt）。
- 系统健康：connected、serverVersion、serverBuildDate。
- 配置健康：apiKeysCount、providers key 数量摘要、价格表覆盖（configured vs used models）、settings 关键开关（usageStatisticsEnabled/loggingToFile/requestLog/wsAuth）。

## 接口/数据来源
- 复用现有后端口径：
  - 系统：`GET /api/system/health`
  - 用量：现有 `app/api/usage/*` 与底层表（UsageEvent/UsageDaily）
  - 管线：`GET /api/usage/aggregate/jobs`
  - 配置：`/api/providers`、`/api/api-keys`、`/api/model-pricing`、`/api/settings`
- 新增（推荐）：`GET /api/dashboard/overview` 聚合端点，一次返回概览页所需数据（避免前端并发拼装造成首屏慢与口径分散）。

## 约束与假设
- 口径一致性：渠道 codex/cliproxy 的归类逻辑必须与现有 usage API 一致。
- 性能：概览页首屏尽量单请求完成；trend/topModels 控制在有限数量点（例如 24–60 个点、Top 5）。
- 安全：所有数据必须通过现有会话鉴权（requireSession），不泄露敏感配置内容。
- 不新增重依赖：优先复用现有 shadcn/ui 组件与图表组件。

## 边界条件
- 过去 24h 无数据：KPI 归零并显示 empty 提示；Top/趋势为空态；引导跳转到用量统计检查筛选。
- 断连/未登录：显示 disconnected/需要登录提示，并提供跳转到系统页。
- 部分数据源失败：允许局部降级（例如配置健康失败不影响用量趋势渲染）。

## 验收标准（可验证）
- 默认进入 `/` 显示过去 24h 概览（A/B/C），信息层级清晰且美观。
- 切换时间窗/渠道后 KPI、趋势、Top Models 同步更新。
- loading/empty/error/disconnected 状态明确。
- 每个区块至少一个有效跳转入口：`/usage`、`/pipeline`、`/logs`、`/system`、`/pricing`、`/settings`。

## 风险与回滚
- 风险：`/api/dashboard/overview` 聚合过重导致首页慢。
  - 缓解：并行查询 + 超时 + 部分降级；必要时拆分端点或延迟加载。
- 风险：日志缺少结构化等级，统计误差。
  - 缓解：v1 只做跳转/最小摘要；统计增强放 P1。
- 回滚：将 `app/(app)/page.tsx` 回退为占位页面。

## 未决问题（若有）
- 请求量口径：v1 使用 UsageEvent count；后续如需与“turns/requests”对齐再调整。
- 日志统计方式：是否新增轻量 `GET /api/logs/stats`（P1）。
