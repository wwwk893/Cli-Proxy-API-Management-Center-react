# 任务计划：登录页登录无效（session 一直 authenticated=false）

- 更新时间：2025-12-31

## 背景

当前在 `http://localhost:3000/login` 点击「登录」后会发起 `/api/auth/login`，但页面仍停留在登录页；同时 `/api/auth/session` 长期返回 `{ authenticated: false }`。

从浏览器 Network 观测到：接口响应会下发 `Set-Cookie: cpa_session=; Max-Age=0; Path=/api/auth ...`（等价于清理 cookie），导致会话无法建立。

另外在本地环境中，3818 端口的 cliproxy 服务仅提供 HTTP（`http://localhost:3818/...` 可达），但前端登录会走到服务端 fetch 访问 management API；若 serverBase 被拼成 HTTPS，则会出现 `无法连接 management API: fetch failed`。

## 根因

1) Cookie 覆盖：`/api/auth/login` / `/api/auth/session` 在同一个响应里对同名 cookie 多次 `res.cookies.set(...)`（不同 Path）会发生覆盖，最终只保留最后一次写入（清理 cookie），导致浏览器没有拿到真正的会话 cookie。

2) 协议不匹配：`lib/auth/session.ts` 的 `buildServerBase` 若硬编码 `https://`，会导致本地（仅 HTTP）cliproxy 服务连接失败，表现为 `fetch failed`。

## 目标

- 登录成功后：浏览器持久化 `cpa_session`（Path=`/`，HttpOnly），并能通过 `/api/auth/session` 验证为 `authenticated: true`。
- 退出登录（`/api/auth/logout`）能可靠清理会话 cookie。

## 范围

- 仅修复登录鉴权链路中“serverBase 拼接 + cookie 写入/清理”逻辑：
  - `lib/auth/session.ts`
  - `app/api/auth/login/route.ts`
  - `app/api/auth/session/route.ts`
  - `app/api/auth/logout/route.ts`
- 不做：不改登录页 UI/交互，不引入新的鉴权机制。

## 验收标准

- 点击登录后跳转到 `next` 或 `/`，且不会被重定向回 `/login`。
- `Application → Cookies` 能看到 `cpa_session`（或 `AUTH_COOKIE_NAME` 对应名称）存在，Path 为 `/`。
- `GET /api/auth/session` 返回 `{ authenticated: true, serverBase, expiresAt }`。
- 点击退出后，`GET /api/auth/session` 回到 `{ authenticated: false }`。

## 风险与回滚

- 风险：浏览器中可能残留“同名不同 Path”旧 cookie，导致读取行为不一致。
- 回滚：回退本次变更文件（见「变更文件清单」）。
